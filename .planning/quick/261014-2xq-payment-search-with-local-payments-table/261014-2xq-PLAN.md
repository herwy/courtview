Persist Padelmates payment records in a local SQLite `payments` table, kept in sync per Europe/London day. Use it to (a) add a name/email search to the Revenue tab's Payment history and (b) fix Top spenders, which currently stops at 2,000 payments (MAX_PAGES=20). Upstream returns oldest first, so for Padium the leaderboard only covers about the first 9 to 10 days of a month.

Purpose: Search finds a player across the whole month, and Top spenders becomes correct. Both stay cheap after the first sync. The user has approved storing payment PII (name, email, phone) persistently in the RPi DB behind the existing token.

Output: backend table, sync, endpoints and unit tests (Tasks 1-2); UI, e2e, docs, deploy and live verification (Task 3).

<decisions>
Open choices resolved by the planner:
- D-A Racketeer search route: a separate `/api/archive/payment-search`. The `/api/archive/` prefix already exempts it from `_block_archived_club`, so the guard stays unchanged. Live `/api/payment-search` keeps getting 410 for Racketeer, which is correct. Both routes share one response builder.
- D-B Crawl politeness: each day is paged sequentially with `random.uniform(0.1, 0.25)` s between pages (same jitter style as `_refresh_loop`). Up to 3 days run concurrently (`PAYMENTS_SYNC_WORKERS = 3`). Why: Padium is about 200 payments/day, so 2-3 pages/day and about 90 requests for a cold month. Fully sequential would take about 60 s, which hits gunicorn's 60 s `--timeout` for an on-demand cold month. Three workers bring that to about 20-25 s, still below the previous leaderboard's 5-way fan-out. The startup backfill does the current and previous month off the request path, so on-demand cold syncs only happen for older months.
- D-C Sync unit = one Europe/London day (fetch [day_start_ms, next_day_start_ms - 1]). Completeness is tracked exactly per day, and a failure only invalidates that day. Safety cap: `PAYMENTS_MAX_PAGES_PER_DAY = 200` (20,000 payments/day). Hitting it marks the day incomplete and logs a warning.
- D-D "Needs sync" rule (implements Required 2, and also covers downtime). Skip a day if its last sync is under `PAYMENTS_FRESH_SECS = 600` old. Otherwise sync it unless it is final. Final = `complete=1 AND synced_at >= day_close + PAYMENTS_FRESH_SECS`, where day_close is the London next-day start. So past days synced after they closed are never re-fetched. Today and yesterday get re-fetched when older than 10 min. A day last synced before it closed (e.g. the service was down over midnight) is re-fetched once. Failed days are retried at most every 10 min, not on every request.
- D-E Club allowlist: payment-search and payment-leaderboard sync only clubs in `HEATMAP_CLUBS` (`PAYMENT_SYNC_CLUB_IDS`). Any other club_id gets 400 `{"error": "club not synced"}`. Arbitrary clubs' PII never lands in the DB, and the endpoint can't be used to make the RPi crawl arbitrary clubs.
- D-F Window validation: start/end are integer ms, end >= start, end - start <= 32 days, otherwise 400. end is clamped to now for syncing (no future days).
- D-G Primary key (club_id, transaction_id). Pre-check in Task 1: if one full Padium day contains duplicate transaction_ids with different status, use (club_id, transaction_id, status) instead and record that in the SUMMARY and docs. If transaction_id is missing, the key is "synthetic:" + createdAt|player_email|amount|status.
- D-H Leaderboard no longer uses stats_cache. After a sync it is a cheap DB query, and the 6h cache would hide the 10-min freshness for the current month. Response shape stays exactly {"leaders": [...]} via `_aggregate_leaders`.
- D-I Search semantics: q is stripped, 2-100 chars, otherwise 400. Matching is case-insensitive (ASCII, SQLite LIKE default) on player_name OR player_email, using `LIKE ? ESCAPE '\'` with `\`, `%`, `_` escaped in that order. The response is {"payments": [<=200 newest first, upstream key names>], "total": N, "limit": 200, "truncated": bool, "complete": bool}. The archive route uses the same filter in Python (casefold substring) over deduplicated archived records within [start, end], with complete=true.
- D-J UI on month/club change: keep the typed query, invalidate any in-flight search, and re-run it for the new month/club once the paged view resets (Racketeer: once the snapshot loads). Racketeer's search window is the month of the selected snapshot.
- D-K Tests: the courtview.py module gets `DB_PATH = os.environ.get("COURTVIEW_DB_PATH", "/root/projects/courtview/courtview_cache.db")` and wraps the module-level call as `if os.environ.get("COURTVIEW_SKIP_STARTUP") != "1": _startup()`. Production behaviour is unchanged because neither env var is set by the unit.
- D-L Hard requirement (coordinator): every new upstream call uses `cffi_requests.get(url, headers=APP_HEADERS, timeout=15, impersonate="chrome110")` through ONE shared helper `_fetch_payment_page`. It replaces the call in api_payment_history and the deleted leaderboard fetch_page, so the expected total is 18 calls, all compliant.
</decisions>
