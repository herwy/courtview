# CourtView: Code Review Report

**Reviewed:** 2026-05-21
**Depth:** deep
**Files Reviewed:** 2
**Status:** issues_found

## Summary

Deep review of the Flask proxy server (`courtview.py`, 1755 lines) and the single-page dashboard (`courtview.html`, 2625 lines). The codebase is well-structured overall with good attention to auth patterns, rate limiting, and WAL-mode SQLite setup. The most serious issues are: a token-bypass window in the proxy OPTIONS handler, an unbounded pagination loop that can be driven by upstream, a missing `Secure` flag on auth cookies, and a cache stampede on all six stats endpoints. Secondary issues cover SQLite connection lifecycle (connections opened without try/finally in several functions), the `api_payment_history` integer-cast of untrusted query params, and stale-cache accumulation. JS issues are mostly cache-invalidation gaps on club switch.

## Critical Issues

### CR-01: OPTIONS pre-flight bypasses auth - proxy leaks 204 to unauthenticated callers

**File:** `courtview.py:1329-1335`
**Issue:** The `proxy` route handles `OPTIONS` and returns 204 immediately before calling `_gate()`. Any unauthenticated client can probe the proxy's CORS posture, confirm it is alive, and enumerate that `Access-Control-Allow-Origin: *` is set, without presenting a token. More seriously, the CORS wildcard header is returned on every proxy OPTIONS response, which contradicts the single-user private-dashboard intent.
**Fix:**
```python
@app.route("/api/<path:p>", methods=["GET", "POST", "OPTIONS"])
def proxy(p):
    passed, via_query = _gate()
    if not passed:
        return _forbidden()

    if request.method == "OPTIONS":
        resp = Response(status=204)
        # Restrict to same-origin only; this app has no cross-origin callers
        resp.headers["Access-Control-Allow-Origin"] = request.headers.get("Origin", "")
        resp.headers["Access-Control-Allow-Headers"] = "Content-Type"
        resp.headers["Access-Control-Allow-Methods"] = "GET, POST, OPTIONS"
        return resp
    # ... rest of proxy
```

### CR-02: Auth cookie missing `Secure` flag - token transmitted in plain HTTP

**File:** `courtview.py:394-402`
**Issue:** `_set_cookie()` and the redirect in `access_page` (line 1431) set the cookie without `secure=True`. The dashboard is accessible over plain HTTP (`http://lab.doxx:8766/`). If any request is made over HTTP, the token is sent in the clear. Even if HTTPS is never used in practice, the flag should be set to prevent the browser from ever sending it unencrypted.
**Fix:**
```python
def _set_cookie(response, token: str) -> None:
    response.set_cookie(
        COOKIE_NAME,
        token,
        max_age=COOKIE_MAX_AGE,
        path="/",
        httponly=True,
        secure=True,      # add this
        samesite="Strict",
    )
```
Also apply `secure=True` to the redirect cookie at line 1431.

### CR-03: Unbounded pagination loop in `api_day_activities` - upstream can cause infinite loop

**File:** `courtview.py:1150-1164`
**Issue:** The `while True` loop in `api_day_activities` terminates only when `len(page) < PAGE_SIZE`. A misbehaving or compromised upstream that always returns exactly 50 records will loop forever, holding a gunicorn thread, burning memory, and blocking other requests (4-thread pool). There is no page cap.
**Fix:**
```python
MAX_PAGES = 20  # 20 x 50 = 1000 activities max
page_num = 0
while page_num < MAX_PAGES:
    ...
    page_num += 1
    if len(page) < PAGE_SIZE:
        break
```

### CR-04: `api_payment_history` - bare `int()` cast on untrusted query param raises 500

**File:** `courtview.py:1224-1225`
**Issue:** `limit` and `skip` are cast with `int(request.args.get(...))` without a try/except. Sending `?limit=abc` or `?skip=` returns a Python 500 traceback (gunicorn default error page), leaking the exception type and stack frame to the caller. Although the caller is authenticated, this is still a correctness bug - 400 is the correct status.
**Fix:**
```python
try:
    limit = min(int(request.args.get("limit", "50")), 100)
    skip  = int(request.args.get("skip", "0"))
except (TypeError, ValueError):
    return jsonify({"error": "limit and skip must be integers"}), 400
```

## Warnings

### WR-01: Cache stampede on stats endpoints - 4 threads can all miss simultaneously

**File:** `courtview.py:498-520, 1034-1046, 1065-1070, 1191-1195, 1264-1267`
**Issue:** `get_stats_cached` / `set_stats_cached` are used by five route handlers with no per-key mutex. When the cache is cold (fresh deploy, after 6h TTL expiry, or on first club switch), all four gunicorn threads can call `get_stats_cached`, all get `None`, and all fan out to upstream concurrently for the same key. On a slow upstream this multiplies by 6 for `api_coach_bios` (6-worker ThreadPoolExecutor inside each of the 4 threads). A simple per-key lock - already done correctly for membership members - prevents this.
**Fix:** Apply the same `_STATS_FETCH_LOCKS` / `_STATS_FETCH_MUTEX` pattern already in `api_membership_members` to `get_stats_cached`. At minimum, add a module-level `threading.Lock()` per endpoint prefix and acquire it before the upstream fetch, then release after `set_stats_cached`.

### WR-02: SQLite connections opened without `try/finally` in several helpers

**File:** `courtview.py:499-508, 511-519, 532-550, 553-573`
**Issue:** `get_stats_cached`, `set_stats_cached`, `get_cached`, and `store_cached` all call `_db_connect()` then `conn.close()` at the end of the happy path. If an exception is raised between `connect` and `close` (e.g. in the JSON parse at line 559-563 inside `store_cached`, or the `conn.execute` inside `get_cached`), the connection is leaked. SQLite with WAL mode and a 10s busy timeout means leaked connections degrade write concurrency. The pattern `conn = _db_connect(); try: ... finally: conn.close()` is already used correctly in `init_db` and `api_heatmap` but not in these helpers.
**Fix:**
```python
def get_stats_cached(key: str) -> str | None:
    cutoff = int(_now()) - STATS_CACHE_TTL
    conn = _db_connect()
    try:
        row = conn.execute(
            "SELECT payload FROM stats_cache WHERE cache_key=? AND fetched_at>?", (key, cutoff)
        ).fetchone()
        return row[0] if row else None
    except sqlite3.Error:
        return None
    finally:
        conn.close()
```
Apply the same pattern to `set_stats_cached`, `get_cached`, and `store_cached`.

### WR-03: `api_month` executes 28 sequential SQLite queries in a single connection - not batched

**File:** `courtview.py:778-789`
**Issue:** The loop executes 28 individual `SELECT` statements inside one connection. Each is a separate round-trip through the SQLite read path. A single query with `IN` or `OR` clauses, or a `WHERE start_datetime IN (...)` bulk select, would be faster and holds the shared WAL read lock for less cumulative time. On a contended 4-thread gunicorn this is measurable.
**Fix:**
```python
# Build all (start_ms, end_ms) pairs first, then query in bulk
params = []
date_map = {}
for i in range(28):
    d = today + timedelta(days=i)
    start_ms = int(datetime(d.year, d.month, d.day, 0, 0, 0, tzinfo=_LONDON_TZ).timestamp() * 1000)
    end_ms   = int(datetime(d.year, d.month, d.day, 23, 59, 59, 999000, tzinfo=_LONDON_TZ).timestamp() * 1000)
    params.append((str(start_ms), str(end_ms)))
    date_map[(str(start_ms), str(end_ms))] = str(d)

placeholders = ','.join(['(?,?,?)'] * len(params))
flat = [(club_id, s, e) for s, e in params for _ in [1]]
# ... build the IN-style query
```
The exact approach depends on SQLite's parameter limit (999 by default), but 28 x 3 = 84 params is well within that.

### WR-04: `api_booked_hours` and `api_revenue_summary` return `payload` variable unbound on non-200 upstream

**File:** `courtview.py:1043-1051, 1196-1211`
**Issue:** In both routes, `payload` is assigned inside `if r.status_code == 200:` but the `Response(payload, ...)` line after the try/except is unconditional. If upstream returns a non-200, `payload` holds the raw content from `r.content.decode(...)` (assigned before the `if`) - which is correct for `api_revenue_summary` (line 1202-1204 assigns unconditionally) but `api_booked_hours` assigns `payload` only inside the `if` block at line 1044-1045. If upstream returns non-200, `payload` is `r.content.decode(...)` (line 1043) because that assignment IS unconditional. However the `Response` then returns the upstream error body with status `r.status_code` - this silently forwards upstream errors to the client. Verify intent: should a non-200 upstream return 502 or pass through?

At a minimum, `api_coach_stats` (line 1269-1276) has the same pattern: it returns `payload` at `r.status_code` unconditionally. All three should check status and return 502 consistently with other routes.

### WR-05: `_stats_key` encodes raw user-controlled `end` string when bucketing fails

**File:** `courtview.py:490-496`
**Issue:** When `int(end)` raises `(TypeError, ValueError)`, `end_bucket` is set to the raw `end` string from the query parameter. This raw value is then embedded in a SQLite primary key via `f"{endpoint}:{club_id}:{start}:{end_bucket}"`. A caller can inject arbitrary strings into the cache key, causing cache misses to accumulate unboundedly (stale entry accumulation) since no TTL-based eviction exists for `stats_cache`. The table has no cleanup mechanism.
**Fix:**
```python
def _stats_key(endpoint: str, club_id: str, start: str, end: str) -> str:
    try:
        end_int = int(end)
    except (TypeError, ValueError):
        return ""   # caller should treat empty key as "no caching"
    end_bucket = end_int // (STATS_CACHE_TTL * 1000) * (STATS_CACHE_TTL * 1000)
    return f"{endpoint}:{club_id}:{start}:{end_bucket}"
```
All callers should skip the cache lookup if `_stats_key` returns `""`.

### WR-06: `_fetch_heatmap_for_club` opens a SQLite connection outside `try/finally`

**File:** `courtview.py:1574-1612`
**Issue:** `conn = _db_connect()` at line 1574 is followed by a `try/except/finally` but only the `conn.close()` is in `finally`. The `conn.commit()` is inside the `try` block, which is correct. However, if any of the `conn.execute(...)` calls raise `sqlite3.Error` (line 1609), the except prints and falls through to `finally: conn.close()` - which is correct. This is actually fine. However, if an exception OTHER than `sqlite3.Error` is raised (e.g. a `KeyError` or `TypeError` in the data transformation above line 1574), it escapes both blocks and `conn.close()` in `finally` is still called. On re-reading: the `try` at 1575 only covers the DB writes. The data transformation (lines 1538-1570) runs before the `conn = _db_connect()`. So this path is safe. This is a non-issue on closer inspection - downgraded to Info level. See IN-01.

### WR-07: `activitiesCache` not invalidated on club switch - stale bookings shown

**File:** `courtview.html:2529-2565`
**Issue:** `switchClub()` resets `monthCache` implicitly by using the club-scoped `cacheKey(CLUB, dateStr)` prefix, but `activitiesCache` uses the same scoped key (`cacheKey(CLUB, isoDate(date))`). However, `switchClub` does NOT explicitly clear `activitiesCache`. The cache key format is `${clubId}/${dateKey}` (line 878), and after switching `CLUB` is updated so new keys are different - BUT any keys that were populated for Club A while Club A was active will remain in the object forever. On a subsequent switch back to Club A they will be reused. If the activity data has changed since the previous visit (which it likely has), stale booking overlays will show.
**Fix:**
```javascript
async function switchClub(id) {
  if (id === CLUB) { toggleClubDrop(false); return; }
  // ... existing code
  activitiesCache = {};  // add this line alongside the other resets
  compareCache    = {};  // compareCache also never evicted (see WR-08)
  // ...
}
```

### WR-08: `compareCache` never evicted - grows without bound across club switches and month navigations

**File:** `courtview.html:872, 1988-2016`
**Issue:** `compareCache` is a module-level object that accumulates keys of the form `${club.id}-${dateKey}`, `rev-${club.id}-${mk}`, and `act-${club.id}-${mk}`. It is never cleared. On a long session with many month navigations, it accumulates entries indefinitely. For a single-tab single-user session on a Pi this is unlikely to matter in practice, but the cache entry for today's date is never refreshed either - if the user leaves the tab open overnight, the Compare tab will show yesterday's availability for "today" indefinitely.
**Fix:** Clear `compareCache` (or at minimum the date-keyed entries) in `switchClub` and when the tab is re-activated after a day boundary.

### WR-09: `renderCourtPopularity` uses `replace` instead of `esc` for court name - partial XSS mitigation

**File:** `courtview.html:2240`
**Issue:** `const name = String(c.name).replace(/</g, '&lt;');` only escapes `<`. It does not escape `>`, `&`, `"`, or `'`. Court names come from the upstream API (via `court_popularity` SQLite table). If a court name contains `&amp;`, `">`, or a `'` used as a quote boundary in an attribute context, XSS is possible. All other similar rendering paths in the file use the `esc()` helper which handles all five characters. This is an inconsistency likely introduced when this section was written.
**Fix:**
```javascript
const name = esc(c.name);
```

### WR-10: `populateNotifyCourts` uses `c._id` which may be `undefined` for v3 courts

**File:** `courtview.html:1645-1651`
**Issue:** `opt.value = c._id;` - but v3-shaped court objects normalised through `normaliseV2` use `court_id` (line 969), not `_id`. The `_id` field only exists on raw upstream v2 objects. After `normaliseV2`, `c._id` is `undefined`, so the select option value becomes `"undefined"`, and `pollWatches` at line 1714 tries to match `c._id === w.courtId` which will never match. Watches set for a specific court will never fire.
**Fix:**
```javascript
opt.value = c.court_id || c._id || '';
```
And in `pollWatches`, line 1714: `padel.filter(c => c.court_id === w.courtId || c._id === w.courtId)`.

### WR-11: `loadStats` and `loadClubInfo` use a `loaded` boolean flag that prevents retry on error

**File:** `courtview.html:1739-1761, 2071-2097`
**Issue:** Both functions set `statsLoaded = true` / `clubLoaded = true` at the start of the function body, before any await. If the fetch fails (network error, 502), the flag remains true and `switchClub` will not re-fetch for this club on subsequent activations of the tab - the user sees the error state permanently until they reload the page. `loadClubInfo` at line 1759 resets `clubLoaded = false` on error, which is correct. `loadStats` does NOT reset `statsLoaded` on failure - line 2072 sets it `true` immediately and there is no reset in any catch path.
**Fix:**
```javascript
async function loadStats() {
  if (statsLoaded) return;
  statsLoaded = true;
  try {
    // ... existing body
  } catch (e) {
    statsLoaded = false;  // allow retry
    // render error state
  }
}
```

## Info

### IN-01: `_heatmap_refresh_loop` runs heatmap fetches on the same thread as the refresh loop, blocking the 24h sleep

**File:** `courtview.py:1615-1631`
**Issue:** The startup stagger loop (lines 1618-1623) calls `_fetch_heatmap_for_club` synchronously. If all three clubs need refreshing, the startup is sequential and slow (3 x network round-trips + SQLite writes), blocking the thread for potentially 45s+ before the first sleep. A simple `threading.Thread` per club (with a small stagger) would parallelize startup refreshes. Low priority for 3 clubs.

---

### IN-02: `stats_cache` table has no cleanup mechanism - stale entries accumulate

**File:** `courtview.py:477-483`
**Issue:** The `stats_cache` table has no `DELETE WHERE fetched_at < ?` maintenance. `availability` is bounded by the 28-day TTL in queries; `stats_cache` is not. Over weeks of use, every unique `(endpoint, club_id, start, end_bucket)` combination accumulates a row permanently. Not a correctness issue, but the DB will grow unboundedly.

---

### IN-03: `_strip_wireslammer` HTML parsing is fragile - nesting counter approach breaks on self-closing tags

**File:** `courtview.py:264-285`
**Issue:** The nesting counter (lines 267-285) increments on `<div` and decrements on `</div>`. This will miscount if the target HTML contains any `<div>` tag inside an attribute value (e.g. `data-x="<div>"`), or if a future version of the source adds another element between the marker and its close. A CSS selector + regex approach, or simply pinning a known byte offset, would be more robust. Low priority since the source HTML is controlled.

---

### IN-04: `api_activity_summary` uses a nested ThreadPoolExecutor inside a gunicorn gthread

**File:** `courtview.py:1087-1092`
**Issue:** `concurrent.futures.ThreadPoolExecutor(max_workers=2)` is created inside a gunicorn gthread worker. This spawns 2 new OS threads per request while the request itself occupies 1 of the 4 gthread slots. Under load, 4 simultaneous requests to this endpoint spawn 8 additional threads. Same pattern in `api_coach_bios` with max_workers=6 (line 1316). This is not dangerous at the current scale (single user) but worth noting.

### IN-05: Hardcoded `NOTIFY_KEY = 'racketeer-watches-v1'` is not scoped by club

**File:** `courtview.html:857`
**Issue:** The notification watches localStorage key is named `racketeer-watches-v1` regardless of which club is selected. Watches are stored per-court-ID which does distinguish clubs, but the key name implies Racketeer-only and would be confusing if the key ever needed to be versioned per-club.

### IN-06: `calcB2B` has O(n^2) inner loop that could be slow for large slot counts

**File:** `courtview.html:1236-1259`
**Issue:** The inner `for j = 0; j < slots.length` loop inside the DFS `while stack.length` iterates all slots for every chain extension. For a fully-available day with 11 courts x 32 slots = 352 slots, worst-case chain depth grows quickly. For typical data this is fast, but it is worth noting in case court counts increase.

### IN-07: `_gate()` and `_check_token()` both implement constant-time comparison independently - duplication

**File:** `courtview.py:376-390, 607-628`
**Issue:** The constant-time token comparison logic (length check + XOR loop) is copy-pasted twice. If a subtle timing bug were ever found in one, the fix must be applied to both. Extract to a single `_constant_time_eq(a, b)` helper.
